# ПР-7 (вариант C): сравнение IPC — pipe, POSIX mq, POSIX shm, Unix socket

## Запуск
```bash
make                          # gcc ... -lrt
./bench.sh                    # 1 ГБ, 4 метода × размеры 64 Б / 4 КБ / 1 МБ -> ipc_results.csv
TOTAL=67108864 ./bench.sh     # быстрая проверка на 64 МБ
./ipc_bench shm 1073741824 4096   # один замер
make check                    # убедиться, что в /dev/shm и /dev/mqueue ничего не осталось
```
Реализация (`ipc_bench.c`): процесс-отправитель шлёт `TOTAL` байт сообщениями по `MSG_SIZE`, потомок-получатель принимает и сверяет число принятых байт.
Время — от `fork` до завершения получателя. Выводится пропускная способность (МБ/с) и **среднее время на сообщение** при потоковой передаче (`время / число сообщений`).
Это не RTT; если хотите именно задержку «туда-обратно», добавьте ping-pong режим с одним сообщением в полёте (см. «Дополнительно»).
* `pipe` — `pipe()`; `sock` — `socketpair(AF_UNIX, SOCK_STREAM)`; у обоих лишние концы закрываются, EOF — закрытие write-конца.
* `mq` — `mq_open/mq_send/mq_receive`, `mq_maxmsg = 10`. **Ограничение ядра:** `/proc/sys/fs/mqueue/msgsize_max` (по умолчанию 8192 Б) — сообщения 1 МБ режутся на куски по 8 КБ (программа печатает предупреждение, в CSV пишется реальный размер).
  Можно поднять лимит: `sudo sysctl fs.mqueue.msgsize_max=1048576` и прогнать без нарезки (укажите это в отчёте).
* `shm` — `shm_open` + `mmap`, кольцо из 8 слотов, синхронизация двумя `sem_t` с `pshared=1` (`empty`/`full`) в самой разделяемой памяти. Получатель копирует слот в локальный буфер (иначе измерение не учитывает чтение данных).
* Завершение: обработчик `SIGTERM/SIGINT` делает `shm_unlink`, `mq_unlink`, посылает `SIGTERM` потомку. Проверено: после `kill -TERM` в `/dev/shm` ничего не остаётся.

## Как объяснять результаты
* **Число копирований.** pipe / socket / mq: данные копируются user → ядро (при `write`/`send`) и ядро → user (при `read`/`recv`) — минимум 2 копирования и 2 системных вызова на сообщение.
  shm: системные вызовы для передачи данных не нужны, но копия в/из общей области остаётся (у вас `memcpy` в слот и из слота). Выигрыш shm — в отсутствии переходов в ядро на каждое сообщение
  (кроме `sem_wait/sem_post`, которые при отсутствии конкуренции работают в пространстве пользователя через атомарные операции; к ядру (futex) обращаются только при блокировке).
* **Малые сообщения (64 Б)** — доминирует стоимость переходов в ядро и синхронизации, пропускная способность низкая (десятки–сотни МБ/с). У shm с одним семафорным обменом на 64 Б накладные расходы тоже заметны (cache-line ping-pong между ядрами).
  Чтобы это показать — пакетная передача (несколько сообщений на один `sem_post`) резко повысит пропускную способность.
* **Большие сообщения (1 МБ)** — стоимость вызова амортизируется, упираемся в пропускную способность памяти (копирование). Различия между методами сжимаются; на pipe влияет размер буфера (`/proc/sys/fs/pipe-max-size`, по умолчанию 64 КБ — большие записи дробятся).
* **mq** сопровождается ограничением на размер сообщения и очередь (`mq_maxmsg`, лимиты `ulimit -q`), поэтому для потоков данных используется редко.

Подтверждение:
```bash
TOTAL=268435456
strace -c -f ./ipc_bench pipe $TOTAL 4096
strace -c -f ./ipc_bench shm  $TOTAL 4096
perf stat -e task-clock,context-switches,cpu-migrations ./ipc_bench pipe $TOTAL 4096   # sudo apt install linux-tools-generic
perf stat -e task-clock,context-switches,cpu-migrations ./ipc_bench shm  $TOTAL 4096
```
Что искать: у `pipe` в `strace -c` — миллионы `read/write`; у `shm` — их почти нет, зато видны `futex`. По `perf stat` сравните `context-switches` и `task-clock`.
(Если `perf` недоступен в ВМ — укажите это; в WSL2 он часто недоступен.)

## Дополнительно (по желанию)
* `splice()`/`vmsplice()` для pipe — передача страниц без копирования в user-space; `io_uring` — пакетная отправка нескольких операций одним системным вызовом.
* Ping-pong режим (RTT): отправитель шлёт сообщение и ждёт ответа тем же методом; задержка = RTT/2 за 10⁵ итераций.

## Контрольные вопросы
* *Почему shm — самый быстрый и самый опасный?* Нет вызовов ядра на каждую передачу и нет защиты от одновременного доступа: синхронизацию пишет программист (гонки проявляются нерегулярно).
* *Запись в pipe без читающих концов?* Процесс получает `SIGPIPE` (по умолчанию завершается), а если сигнал игнорируется — `write` возвращает `-1` с `errno = EPIPE`.
