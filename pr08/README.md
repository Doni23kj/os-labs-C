# ПР-8 (вариант C): обедающие философы на pthreads, TSan/helgrind, deadlock в ядре

## Запуск
```bash
make
./philosophers naive 10            # deadlock: программа сама заметит отсутствие прогресса
./philosophers ordered 10          # упорядоченный захват
./philosophers trylock-fixed 10    # trylock + откат, одинаковая задержка (возможен livelock)
./philosophers trylock-rand 10     # trylock + откат, случайная задержка
./philosophers waiter 10           # официант: семафор N-1
make all-variants                  # все варианты, вывод в stats_*.txt
make tsan                          # ThreadSanitizer; make helgrind  (нужен valgrind)
```
Для каждого варианта выводится: число приёмов пищи у каждого философа, максимальное время ожидания вилок, итог.
Философ считается «ещё голодным», если в момент остановки находится в ожидании вилок (его текущее ожидание учитывается в максимуме).

## Как убедиться, что naive «завис» (программа с deadlock «как есть»)
```bash
PHIL_NODETECT=1 ./philosophers naive 10 &
P=$!; sleep 3
ps -L -o pid,tid,stat,pcpu,wchan:20 -p $P          # все 5 потоков в futex_wait, CPU ≈ 0 %
gdb -p $P -batch -ex 'thread apply all bt'         # у каждого философа в стеке pthread_mutex_lock -> take_forks
cat /proc/$P/task/*/status | grep -E 'State|Name'  # State: S (sleeping)
kill $P
```
Признак deadlock: приёмы пищи не растут, потоки спят (CPU ≈ 0). Признак livelock (trylock-fixed): приёмы пищи не растут, но потоки **активны** (CPU > 0, `top -H`).

Для ориентира — мой тестовый прогон на 1 ядре (5 с; ваши числа будут другими):
* naive: зависло примерно после 260 приёмов у каждого, программа сообщила «нет прогресса»;
* ordered: ≈8800 приёмов, но **неравномерно** (1357 … 2055): упорядочивание исключает deadlock, но не гарантирует справедливость (философ 4 берёт сначала вилку 0 — конкурирует с философом 0);
* waiter: ≈5100 приёмов, почти поровну (1020 … 1023) — официант даёт самую ровную раздачу в этом прогоне, но и самую низкую суммарную пропускную способность (одно место за столом простаивает);
* trylock-*: ≈6500 приёмов, равномерно.

**Про livelock.** На моём 1-ядерном стенде livelock у `trylock-fixed` **не** воспроизвёлся — потоки не идут в такт из-за планировщика.
Чтобы его показать, на многоядерной машине уменьшайте джиттер: одинаковая задержка во всех потоках, старт через барьер (уже есть), задержки `usleep(200)` между захватом левой вилки и `trylock` правой (уже есть),
а также можно закрепить потоки по ядрам (`taskset`) и уменьшить время еды. Если не воспроизводится — так и напишите, показав попытки; это честный результат. Livelock определяется так: еда не растёт при ненулевом CPU.
Максимальное время ожидания в `trylock-fixed` против `trylock-rand` — основная метрика сравнения.

## ThreadSanitizer / helgrind: что находят и что нет
Мой прогон (`./philosophers_tsan <variant> 3`; воспроизведите и запишите свой результат, особенно для naive и waiter):
| вариант | что показал TSan | комментарий |
|---|---|---|
| ordered | ничего | корректно: порядок захвата единый |
| trylock-rand | ничего | `trylock` не создаёт ожидания, цикла нет |
| waiter | `lock-order-inversion (potential deadlock)` | **ложное срабатывание**: инструмент видит только порядок мьютексов (0→1, 1→2, …, 4→0) и не знает, что семафор «официанта» не пускает пятого философа за стол |
| naive | в моём прогоне предупреждения о порядке не вывелось (программа ушла в реальный deadlock и завершилась через `_exit`) — **проверьте у себя**; обычно ожидается lock-order-inversion | инструменты фиксируют *потенциальные* циклы по порядку захвата, а не сам факт зависания |

Первый прогон выявил ещё и «thread leak» (потоки не join-ились) — исправлено: при штатном завершении все потоки join-ятся; при deadlock join невозможен, поэтому `_exit`.
Вывод: TSan/helgrind (lock-order inversion) ловят **потенциальные** инверсии порядка захвата мьютексов даже если deadlock в этом запуске не случился, но
* не видят зависимостей через семафоры/условные переменные/pipe (отсюда ложное срабатывание на `waiter`);
* не ловят livelock (никто не блокируется);
* могут не дойти до отчёта, если процесс завис/завершён аварийно.

## Как ядро Linux обнаруживает deadlock (по документации)
Проверьте формулировки по `Documentation/locking/lockdep-design.rst` и `Documentation/admin-guide/sysctl/kernel.rst` (`hung_task_*`).
* **lockdep** (`CONFIG_PROVE_LOCKING`) — валидатор блокировок *внутри ядра*: строит граф зависимостей между «классами» блокировок и сообщает о циклах и небезопасном использовании (например, захват в обработчике прерывания и вне его) **до** фактического зависания.
  Работает только для примитивов ядра (spinlock, mutex, rwsem…) и только в отладочных сборках — накладные расходы велики.
* **hung_task** (`kernel.hung_task_timeout_secs`, по умолчанию 120 с) — поток ядра проверяет задачи в состоянии `TASK_UNINTERRUPTIBLE` (D), не получавшие CPU дольше таймаута, и печатает «task … blocked for more than 120 seconds» со стеком (можно настроить panic).
* **Почему пользовательские deadlock ядро не обнаруживает.** Заблокированный на `pthread_mutex_lock` поток спит в `futex_wait` в *прерываемом* состоянии (S) — это нормальное состояние и для здорового процесса, который просто чего-то ждёт, поэтому `hung_task` его не трогает.
  Для обычного futex ядро не знает, какой поток «владеет» мьютексом (владельца хранит пользовательская память), поэтому не может построить граф ожидания; граф ожидания пользовательских мьютексов может строить только библиотека/инструмент (TSan, helgrind, ваш `TrackedLock` из варианта B).

## Контрольные вопросы
* *Почему упорядочивание захвата ресурсов исключает deadlock?* — Нарушается условие «циклическое ожидание»: при глобальном порядке цепочка «жду ресурс с большим номером, держа меньший» не может замкнуться в цикл.
* *Почему алгоритм банкира редко применяют в универсальных ОС?* — Нужно заранее знать максимальные потребности процессов, число процессов и ресурсов должно быть фиксированным, проверка безопасности дорога.
