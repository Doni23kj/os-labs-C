# ПР-2 (вариант C): копирование файла и системные вызовы

## Запуск
```bash
make
SIZE_MB=100 ./bench.sh          # results.csv + buffer_time.png (медиана из REPEAT=3 повторов)
./syscall_write
```
Подтверждение через strace:
```bash
strace -c -f ./copy rw big.tmp out.tmp 1
strace -c -f ./copy rw big.tmp out.tmp 65536
strace -c -f ./copy stdio big.tmp out.tmp 1
strace -c -f ./copy sendfile big.tmp out.tmp
strace -c -f ./copy cfr big.tmp out.tmp
```
(буфер 1 Б под strace очень медленный — для strace используйте файл 1–5 МБ).

## Объяснение
* **read/write, буфер 1 Б**: на 100 МБ это 10⁸ пар вызовов. Каждый системный вызов — переход user→kernel→user
  (смена режима, сохранение регистров, проверки безопасности), порядка сотен наносекунд. Отсюда десятки секунд.
  С ростом буфера число вызовов падает в `размер` раз, время быстро падает и выходит на «полку»: дальше ограничивает скорость памяти/диска.
* **fread/fwrite**: stdio сама буферизует (по умолчанию порядка 4 КБ), поэтому `fread(…,1,…)` почти не обращается к ядру на каждый запрос:
  `read/write` вызывается примерно `размер/4096` раз, хотя сами функции libc вызываются столько же раз, сколько и раньше (это обычные вызовы функций в user-mode, на порядки дешевле системных).
  Поэтому stdio при буфере 1 Б заметно быстрее «сырого» read/write при буфере 1 Б; при больших буферах разница исчезает. Проверьте по `strace -c`.
* **syscall(SYS_write)** даёт тот же результат, что `write()`: обёртка libc лишь кладёт номер вызова и аргументы в регистры и выполняет инструкцию `syscall`, плюс обрабатывает `errno`.
* **sendfile / copy_file_range** быстрее: данные не покидают ядро, нет копирования ядро→user→ядро и лишних переходов на каждый блок;
  `copy_file_range` на некоторых ФС (btrfs, XFS) может вообще не копировать данные (reflink).

## Контрольные вопросы
* Почему нельзя обратиться к диску напрямую? — В режиме пользователя нет привилегий на ввод-вывод; доступ разделяет и защищает ядро.
* Что дороже — вызов функции или системный вызов? — Системный (смена режима, проверки, влияние на кэши/TLB).
