# ПР-5 (вариант C): MLFQ, nice/CFS, SCHED_FIFO, EEVDF

## Запуск
```bash
make
./sched --algo srtf set1.txt             # эталон: wait 6.50, turnaround 13.00
./sched --algo rr --quantum 3 set1.txt   # эталон: wait 13.50, turnaround 20.00
./sched --algo mlfq --quantum 4 --boost 50 --gantt set3.txt
./compare.sh                             # сводная таблица
./nice_exp.sh 20                         # nice vs веса CFS (root не нужен)
sudo ./fifo_exp.sh 10                    # SCHED_FIFO (в ВМ!)
```
Симулятор написан на C (посекундный; соглашения об очередях — как в «Исходных данных»: прибывший в момент t ставится раньше вытесненного; вытеснение в SRTF только при строго меньшем остатке).
SRTF и RR(q=3) на set1 совпали с эталоном, значит соглашения реализованы верно.

## 1. MLFQ
Три уровня, RR на каждом, квант растёт ×2 (при `--quantum 4`: 4, 8, 16). Новый процесс — на верхний уровень; израсходовал квант — вниз;
каждые `--boost` тактов все процессы возвращаются на верхний уровень (против голодания); при появлении процесса на более высоком уровне текущий вытесняется.
Длительность burst алгоритм **не знает**.

Результаты (детерминированные; можно перепроверить `./compare.sh`):
| набор | алгоритм | ср. ожидание | ср. оборот | ср. отклик | переключений |
|---|---|---|---|---|---|
| set1 | SRTF | 6.50 | 13.00 | 4.25 | 4 |
| set1 | RR q=3 | 13.50 | 20.00 | 3.00 | 9 |
| set1 | MLFQ | 11.75 | 18.25 | 4.50 | 6 |
| set2 | SRTF | 132.80 | 151.55 | 132.80 | 19 |
| set2 | RR q=3 | 259.20 | 277.95 | 26.95 | 130 |
| set2 | MLFQ | 269.95 | 288.70 | 17.15 | 101 |
| set3 | SRTF | 13.95 | 19.70 | 11.00 | 22 |
| set3 | RR q=3 | 26.85 | 32.60 | 17.05 | 30 |
| set3 | MLFQ | 16.50 | 22.25 | 13.20 | 21 |

**Вывод.** На смешанной нагрузке (set3: один длинный процесс + много коротких) MLFQ (ожидание 16.50) заметно ближе к SRTF (13.95), чем RR (26.85):
короткие процессы укладываются в первый квант и заканчиваются на верхнем уровне, а длинный «оседает» вниз — то есть MLFQ сам выявляет короткие задачи без знания burst.
На set2 (все процессы CPU-bound и примерно одинаковые) приближения к SRTF **нет** и быть не может: все быстро опускаются на нижний уровень и MLFQ ведёт себя как RR
(SRTF здесь выигрывает за счёт того, что в «чистом» виде обслуживает по очереди; цена — отклик 132.8 против 17.15). Это честный результат: MLFQ приближается к SRTF только когда в нагрузке есть различимые короткие задачи.
Влияние параметров на set3 (ожидание): квант 1 → ≈25.5, квант 2 → 24.15, квант 4 → 16.5; boost на этом наборе почти не влияет (на коротком горизонте голодание не успевает проявиться) — проверьте `--boost 0/50/200`.

## 2. nice и веса CFS (`nice_exp.sh`)
4 CPU-bound процесса закреплены на одно ядро (`taskset -c 0`) с nice 0, 5, 10, 15; доля CPU берётся из первого поля `/proc/PID/schedstat` (время на CPU в нс).
Веса CFS (`sched_prio_to_weight`): nice 0 → 1024, 5 → 335, 10 → 110, 15 → 36. Ожидаемая доля = вес / сумма весов: 68.0 %, 22.3 %, 7.3 %, 2.4 %.
Пример прогона (6 с, моя тестовая среда; **у вас — свой вывод**): 67.9 %, 22.3 %, 7.3 %, 2.5 % — совпадение в пределах десятых долей процента.

## 3. SCHED_FIFO (`fifo_exp.sh`)
Один `burn` под `chrt -f 10`, три обычных (SCHED_OTHER) на том же ядре. В тестовой среде FIFO-процесс получил ≈ 94 % CPU, остальные три — по ≈ 2 %.
Объяснение: RT-класс строго приоритетнее обычного; FIFO-процесс не вытесняется по кванту, пока сам не заблокируется или не появится RT-процесс с большим приоритетом.
Остальные получают CPU только благодаря ограничению RT-времени (`sched_rt_runtime_us=950000` из `sched_rt_period_us=1000000`, т. е. 95 %): оставшиеся 5 % делят обычные процессы.
Без этого лимита (значение −1) бесконечный цикл на FIFO заморозил бы ядро. Вставьте свой вывод: `<<ВСТАВИТЬ>>`.

## 4. EEVDF (дополнительно, ядро ≥ 6.6)
Прочитайте `Documentation/scheduler/sched-eevdf.rst` и статью LWN «An EEVDF CPU scheduler for Linux» и проверьте `uname -r` на своей машине. Кратко (проверьте формулировки по источникам):
* CFS выбирает задачу с наименьшим `vruntime` (самую «обделённую») и использует эвристики (например, бонус сна) для интерактивных задач.
* EEVDF (Earliest Eligible Virtual Deadline First) выбирает среди «имеющих право» (eligible — не получивших больше положенной доли; lag ≥ 0) задачу с наиболее ранним виртуальным дедлайном = начало + (срез / вес).
  Короткий запрашиваемый срез (latency-nice / `sched_attr.sched_runtime`) → ранний дедлайн → задача быстрее получает CPU, не получая при этом большей доли в долгосрочной перспективе.
* Практический эффект: задержка отклика интерактивных задач управляется явно (срез), а не эвристиками.
Опционально измерьте задержку отклика под нагрузкой: `cyclictest`-подобный цикл `usleep(1000)` с замером запаздывания при работающих `burn`.

## Контрольные вопросы
* SJF нельзя применить напрямую — длительность следующего burst заранее неизвестна (можно лишь предсказывать экспоненциальным усреднением).
* RR при кванте → ∞ вырождается в FCFS.
