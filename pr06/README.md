# ПР-6 (вариант C): спинлок, читатели–писатели, TSan, монитор

## Запуск
```bash
nproc                         # указать в отчёте; для спинлока нужно >= 4 ядер
make
./spin 1000000 20000 | tee spin.csv     # спинлок TAS/TTAS против pthread_mutex; 2, 4, 16 потоков; короткая/длинная секция
./rw reader 3                 # приоритет читателей: писатель голодает
./rw fair 3                   # без голодания писателя
./bounded monitor; ./bounded sem
make tsan                     # ThreadSanitizer (все программы должны пройти без предупреждений)
make helgrind                 # то же под valgrind --tool=helgrind (если установлен valgrind)
```

## 1. Спинлок против мьютекса (`spin.c`)
Спинлок на `__atomic_exchange_n` (TAS) и его улучшение TTAS (крутимся на чтении, пишем только когда замок выглядит свободным, — меньше трафика когерентности кэша).
Короткая секция — один инкремент; длинная — ≈1000 пустых итераций (порядка микросекунды). Корректность проверяется итоговым значением счётчика.

Таблица (вставьте **свои** числа, с `nproc`):
| секция | потоков | TAS, с | TTAS, с | mutex, с |
|---|---|---|---|---|
| короткая | 2 | `<<>>` | | |
| короткая | 4 | | | |
| короткая | 16 | | | |
| длинная | 2 | | | |
| длинная | 4 | | | |
| длинная | 16 | | | |

Как объяснять (проверьте по своим данным, они могут отличаться):
* **Когда выигрывает спинлок**: секция очень короткая, потоков не больше ядер, держатель замка не вытесняется планировщиком. Ожидающий не засыпает — нет системных вызовов (futex) и переключений контекста (десятки сотен нс–мкс).
* **Когда проигрывает**: потоков больше, чем ядер, или секция длинная — ожидающие впустую жгут CPU (а если держателя вытеснили, то целый квант), мьютекс усыпляет ожидающих и отдаёт ядро.
  На 16 потоках и малом числе ядер спинлок обычно заметно хуже. На 1 ядре спинлок вообще бессмысленен.
* TAS против TTAS: TAS непрерывно пишет в общую кэш-линию, она «пингуется» между ядрами; TTAS читает из локального кэша, пока замок занят.
* `pthread_mutex_t` в glibc сначала быстро пытается атомарно захватить замок и только потом уходит в `futex` — поэтому на коротких секциях он ближе к спинлоку, чем кажется.

## 2. Читатели–писатели (`rw.c`)
Своя реализация на мьютексе и двух условных переменных. Инвариант проверяется в коде: писатель делает `a++`, паузу, `b=a`; читатель обязан всегда видеть `a == b`
(иначе растёт `invariant_violations`; в обоих режимах = 0).

* `reader` (приоритет читателей): читатель входит, пока нет *пишущего*, игнорируя ждущих писателей. 4 читателя, перекрывающиеся по времени, никогда не опускают счётчик читателей до 0 — писатель не получает доступа.
* `fair`: ждущий писатель (`waiting_w > 0`) блокирует вход новых читателей; существующие дочитывают, затем пишет писатель.

Результат тестового прогона (2 с; у вас цифры будут другими, суть та же):
```
mode=reader  reads=12793  writes=1    max_writer_wait=2.001s  invariant_violations=0   <- голодание писателя
mode=fair    reads=11921  writes=749  max_writer_wait=0.002s  invariant_violations=0
```
Цена справедливости — немного меньше чтений (читатели иногда ждут писателя).
(В `reader` единственная запись и `max_writer_wait ≈ 2 с` — писатель получил блокировку только когда читатели остановились по флагу.)

## 3. Ограниченный буфер (`bounded.c`): монитор против семафоров
3 производителя, 2 потребителя, 1000 элементов, буфер 5. Проверка: каждый элемент получен ровно один раз, переполнение → `exit(2)`.
* Монитор: данные + мьютекс + условные переменные в одной структуре; условия (`count == CAP`, `count == 0`) видны прямо в коде, как `while`-цикл.
* Семафоры: «пустые слоты» и «заполненные слоты» кодируют те же условия счётчиками; кода меньше, но смысл неявный (нужен отдельный мьютекс на индексы, нетривиальное завершение — «отравленная таблетка»).
* Исправлена ошибка завершения в режиме семафоров: сравнение `shead == stail` принимало заполненный кольцевой буфер за пустой и могло досрочно останавливать потребителя. Теперь число элементов `scount` проверяется и изменяется под мьютексом.
* Именованные POSIX-семафоры `sem_init` на macOS не поддерживаются; режим `sem` необходимо проверять на Linux. Ошибка инициализации теперь печатается, вместо запуска с неинициализированными семафорами.
* Читаемость: монитор проще рассуждать о корректности (инвариант в одном месте) и расширять (новое условие — новая `cond`); семафоры компактны, но легко ошибиться в порядке `wait` (дедлок: сначала мьютекс, потом семафор).

## 4. ThreadSanitizer / helgrind
Первый прогон `rw.c` под `-fsanitize=thread` дал **находку**: гонка по флагу остановки `stop` (`volatile int`, пишет `main`, читают потоки).
`volatile` не является синхронизацией в C — это формально data race. Исправлено на `__atomic_load_n/__atomic_store_n`.
После исправления `make tsan` проходит чисто для `bounded` (оба режима) и `rw` (оба режима).
Если у вас helgrind/TSan покажут другие предупреждения — исправьте и перечислите в README (что нашли → почему гонка → как исправили).

## Контрольные вопросы
* Семафор(1) против мьютекса: у мьютекса есть владелец (освобождать должен тот, кто захватил; бывают приоритетное наследование и проверки ошибок), семафор можно «поднять» из другого потока — им удобно сигнализировать.
* Условная переменная без мьютекса нельзя: проверка условия и уход в ожидание должны быть атомарны относительно изменения условия, иначе «потерянное пробуждение».
